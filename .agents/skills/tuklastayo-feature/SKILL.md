## Workflow

1. Inspect the feature's existing packages, route, rendering, contracts, ViewModel, use cases and DI wiring. Identify the owner of each responsibility before editing. Keep the existing feature package prefix; keep Route, Screen, ViewModel, UiState and Intent together at screen level, with optional component/ and debug preview/ packages. Do not add presentation/ or mandatory contract/model/mapper packages. Koin initialization/composition stays in app. Do not reorganize unrelated features.
2. Give Screen, ViewModel, UiState, Intent and DI declarations separate appropriately named Kotlin files. Follow Route -> Screen -> Components -> Preview. Routes own existing Koin ViewModel resolution, lifecycle-aware StateFlow collection, intent dispatch and navigation/application callbacks. Screens accept immutable UiState and callbacks and must render independently without ViewModel lookup, flow collection, DI/Firebase/navigation initialization, repositories or use cases. Local UI-only state is allowed. Use immutable UiState and sealed Intent; add a separate Effect file only for a needed one-time event. Keep small private helpers with their owner; never generate empty contracts/classes or split every function for symmetry.
3. Implement or reuse concrete domain use cases. ViewModels call use cases through constructor injection and expose read-only StateFlow. Handle request concurrency deliberately and propagate coroutine cancellation.
4. Keep Compose focused on rendering state and dispatching intents. General-purpose shared components belong in core:designsystem; feature-specific components belong in the feature. Both the Gallery and screens consume the same production implementations. Collect state with lifecycle awareness; keep navigation callbacks in the route/app layer. Reuse designsystem components. Follow root naming: branded code uses `Tuklas` (types/composables PascalCase, functions/properties camelCase), user-facing product text stays `TuklasTayo`, and ordinary feature/domain names stay unprefixed. Keep application ID and code namespace distinct as specified in AGENTS.
5. Keep feature repository, use-case and ViewModel declarations in feature di/; app-level di/AppModules.kt composes them; app owns navigation/backend selection. If data changes are needed, keep contracts backend-independent and backend implementations/DTO mapping in feature Data packages; domain-to-presentation mapping stays in screen or justified shared mapping package. Never inject a concrete repository into a ViewModel or expose SDK types in presentation contracts.
6. Add debug-only previews under debug preview/ using the actual production Screen and offline sample UiState, wrapped in TuklasTheme (and Surface when a background is needed). Include Light/Dark for important screens and loading/content/empty/error when supported; add a sample provider only when useful. Keep fictional fixtures and tooling dependencies out of release. Never create preview-only screen copies or new business states for examples. Keep contracts in screen package and feature components in component/ when appropriate. Stateless placeholders and the local-state Gallery need no ViewModel or Route just for symmetry.
7. Default to Light validation: compile only the affected scope once. Run focused tests when changed logic, moved test imports, or a concrete regression risk warrants them. No full suites, lint, instrumentation or release build unless requested or specifically justified. Respect workspace/cache/external-access limits; provide manual steps for blocked checks. Update only affected documentation.

## Feature-owned Clean Architecture

- Active modules: :app, :feature:discover, :feature:manage, :core:designsystem. Each feature owns its Domain, Data and Presentation responsibilities, use cases, repository interfaces, implementations, models, mappings and tests. No shared business core modules or cross-feature dependencies without an actual cross-feature contract requirement.
- Discover uses com.lakbay.tuklas.feature.discover.domain (model/repository/usecase), data (dto/repository), and its existing screen packages (explore/search/saved/place_detail/shared/navigation). Existing screen packages are its Presentation layer; do not add redundant presentation nesting or empty layers merely for symmetry.
- Manage owns its independent dashboard/navigation Presentation and all future management Domain/Data logic. It currently needs no repositories, use cases or business models: do not invent editing, publication, queue, permissions, statistics or empty package scaffolding.
- Within each feature, Presentation -> Domain and Data -> Domain. Domain stays pure Kotlin without Android, Compose, Firebase, DI, Data or UI imports. ViewModels call feature-owned use cases, never repositories or SDKs directly. DTO/backend mapping stays in feature Data. Use domain models directly where sufficient; optional UI projections require meaningful formatting/display behavior.
- App owns Application/Activity startup, root navigation, build configuration, app/auth session and Google sign-in integration and Koin initialization/composition. Features provide their own DI definitions; app selects the backend flag and composes modules. Discover's discoverModules(useFirebase) owns its repositories, use cases and ViewModels. Mock remains default; debug fixtures and photos remain debug-only, release mock data is empty.
- Both features depend on :core:designsystem for generic reusable UI only. Discover and Manage never depend on one another or app; app imports feature integration APIs rather than internal business implementations. No generic base ViewModels/MVI/navigation framework, extra Activities or per-screen modules.
- App root NavHost owns experience integration; Discover and Manage own internal NavHosts/Scaffolds with controllers scoped to their graphs. Preserve one Activity, approved Discover UI, Search keyboard/back behavior, tab restoration, carousel semantics and lifecycle, Gallery source-set hooks and previewability. No legacy Explore feature.
- App-owned Google authentication is implemented (requires real Firebase setup). Discover remains guest-accessible. Restaurant authorization is not implemented; keep Manage unregistered until verified restaurant authorization and backend enforcement exist. Owner preference/debug mode never grants authorization. Manage previews/tests may instantiate UI directly without granting access.
- Route -> Screen -> Components -> Preview and screen-level immutable MVI remain mandatory. Keep Route/Screen/ViewModel/UiState/Intent together, with optional justified subpackages/effects. Koin initializes only in app. Previews use offline production Screens with TuklasTheme and require no backend/runtime initialization.
- :core:designsystem stays shared because it provides generic UI infrastructure, never feature business contracts. Gallery and all feature consumers reuse its production components; no duplicated styling or business-model dependencies.
- Preserve the documented canonical places schema, existing Firebase/mock selection, cancellation/error semantics and repository contracts. Do not introduce published/approval fields, migrate production data or invent management persistence rules. See docs/DATA_SCHEMA.md before implementing future management persistence.
- Tests belong to the owning feature. Use one :app:assembleDebug plus directly relevant targeted unit tests; no broad suites, lint, instrumentation or release builds by default. Existing no-PC-control, workspace, external-access, Git safety and dependency-version restrictions remain unchanged.
Profile belongs to Discover as presentation-only ProfileScreen/ProfileUiState; app projects its auth state and supplies callbacks. App owns separate LoginScreen/auth operations/root routing. Never pass app-owned AuthUser/LoginUiState/ViewModels into Discover, import Firebase in Profile, duplicate session observation, or expose Manage on authentication alone. Preserve the main tab/scroll state when Login is pushed/popped.
